# Shields_Knight 方向

> 基准：代码 V0.1.0.5（`8d572af`）

## 一、当前判断

### 1.1 一句话

骨架是对的，投影面是错的，数据还住在代码里。

### 1.2 根问题一：投影面太宽

- **症状**：`RenderData` 搬的是整个 `Button`，连带 `hoverThreshold`、`hoverStartTime` 这些渲染层一个字都用不上的逻辑内部状态一起搬。
- **代价**：加一个品种就要往 `RenderData` 加一个 `vector`；加一个视觉属性就要改类型。渲染层开始被迫知道"画的是什么品种"。
- **判据**：快照该描述"怎么画"，不该描述"画什么品种"。品种属于数据，不属于类型。

`render.cpp` 里按 `ButtonID` 散写 if-else，不是偷懒——是类型里没有"怎么画"这个概念，只能靠代码分支补。

### 1.3 根问题二：数据住在代码里

- **症状**：`config_rect.h`、`config_button_table.h` 全是 `inline constexpr`。
- **代价**：改一个数值要重编；热重载没有地方接；实体表写不出来（上千条 constexpr 不可维护）。
- **判据**：能被改的东西必须能在运行时被替换。

所有"数据化"的路都堵在这一个决定上。

### 1.4 其余结构性缺口

- 命中区与绘制区是两套来源（`1.3f` 是这个缺口的产物，不是独立 bug）
- 渲染层没有资源所有权（函数内 `static` 纹理 + 循环内局部纹理）
- `logic` 反向依赖 `render` 类型（`logic.h` include 了 `type_render_data.h`）
- 没有"一帧"的完整概念（`RenderData` 不是 POD，里面装着带计时的逻辑对象）
- 没有 dt，只有绝对时间

### 1.5 不能删的资产

| 资产 | 为什么不能删 |
|---|---|
| 分层 tick 顺序 | 状态机 → 结算意图 → 提交渲染。顺序错了，后面全是补丁 |
| 数据 / 意图分离 | 发意图的人不依赖执行的人 |
| 立即模式渲染 | 不持有长生命周期画面对象，渲染只消费快照 |
| `Screen` + `sf::View` letterbox | ~150 行，正确且完整，能扛任意窗口尺寸 |
| 表驱动的可点注册表 | 这就是"虚体"应有的形状，只是名字叫 Button |
| 栈式状态机 | push / pop / replace 语义干净 |
| 双工具链 + 字符集处理 | 一份源码 MinGW / MSVC 都能编，VS 可断点，中文不乱码 |

## 二、接下来三步

### 第 1 步：收窄渲染契约（核心）

交付：`Config` 运行时结构 + 适配器 + 统一的 `drawLayer` + 纹理缓存。

判据：渲染层从此只认识 `DrawItem`，不认识 `Button`；加一个新按钮只改表。

### 第 2 步：让数据离开代码

交付：JSON 读取 + 配置校验 + 失败回退 + 手动重载。

判据：改一个数值不用重编。

真价值不是省编译（全量重编才十几秒），而是给实体表铺路 + 改配置不丢游戏状态。只为了调几个 UI 坐标而做它，不值得。

### 第 3 步：业务地基

交付：dt → 实体 → 第一段动画。

判据：`PuGame` 里能跑起一个会动的东西。

### 顺序理由

第 1 步不做完，第 2 步没有结构可填；第 2 步不做完，第 3 步的实体表无处可放。

## 三、AI 的建议

### 3.1 依赖方向

- **适配器放 render 层，不要放 logic。** `logic` 一旦知道"美术怎么画"就会重新变成上帝对象，而现在的 `render.cpp` 散写 if-else 正是同一个病根的另一面。放 render 层还能顺手剪掉那个反向依赖，让依赖单向。
- **`logic` 不应该认识 `DrawItem`。** 适配器是逻辑世界与渲染世界之间唯一的桥，桥上只走 `Config` 和几个窄视图。桥出现两个方向，说明分层没做成。
- **不要让 `commitRenderData()` 留在 logic 里当委托。** 那等于把适配器藏在 logic 里，下次有人往这个函数里加逻辑，你就回到了宽快照。

### 3.2 快照的形状

- **按"绘制层"分组，不要按"逻辑品种"分组。** 按品种分组（`vector<Button>` / `vector<Knight>`）等于把手写 type 的痛换个地方复发——每加一个品种都要新集合 + 新渲染函数 + 新 for。按绘制路径分组，加品种只是加一条表项。
- **类型只描述"怎么画"，品种属于数据。** 判据很硬：`DrawItem` 的字段数应该恒定。要加第 5 个字段之前，先问"这能不能用 `(art, flags)` 的组合表达"——大概率能。
- **分类的唯一理由是顺序，不是分别写代码。** 背景 / 世界 / UI / 覆盖四个层共用同一个 `drawLayer`，因为它们是同一个类型。哪天某个层需要不同的绘制路径（混合模式、顶点流），才该开新类型。
- **将来的异构绘制用 `std::variant` + `std::visit`，不要用虚接口。** 值语义、零堆分配、无生命周期同步，漏分支编译器直接报错；它和快照天然兼容，而虚函数池和快照是互斥的两条路。

### 3.3 现在不要做的

- **不要上对象池 / 虚接口。** 成本量级完全不同：快照是 `O(数据量)`，对象池是 `O(生命周期管理)`。你的数据量是"20 个 24 字节结构体"，撑不起稳定 id + 代际句柄 + 脏标记这套设施，而它会把 DEVLOG 里已经论证过要避开的"注册 / 同步 / 销毁三件套"原样请回来。
- **不要写"几乎不调用"的接口。** 实体的按下 / 悬停接口属于此类——答不出"调用者是谁、什么时候调"就别写。README 里已经在列死代码了，那是净负债。
- **不要用继承做虚体。** 继承会把"能点"塞给不该点的东西（血条、buff、伤害飘字），还会跟 `common.h` 里那句"再也不敢 const 了"的疤同源——继承体系会给同类问题成倍放大。

### 3.4 性能与内存

- **每帧全量重建是最终形态，不是妥协。** 语义上"只活一帧"（里面没有跨帧对象），实现上持有一个实例 `clear()` 后复用——`clear()` 不释放 capacity，所以第二帧起零分配、零字符串拷贝。
- **纹理缓存只做一件事。** 按需加载一次、失败返回 1×1 白图、只报一次错。顺手就把每帧 2.8MB 解码修掉了，是当前性价比最高的一处改动。
- **等真的是 5000 个实体、每帧只动 3 个时再谈增量更新。** 到那时你会先加空间分区和裁剪，还轮不到脏标记。

### 3.5 数据与配置

- **config 必须是运行时对象，不能是 `inline constexpr`。** 这是数据化、热重载、实体表三条路的共同闸门，不打开它，后面每一个都做不成。
- **差异必须来自数据表，不能来自代码里的魔法数。** `1.3f` 是坏的（代码里拍脑袋），帧表里的 `offset` 是好的（数据里写明的抖动）。这是"命中与绘制同源"的精确版：两张矩形**可以**不等，但不等的原因必须在表里。
- **热重载做"手动触发 + 原子换"就够了，不要做文件监听。** 校验失败必须回退到上一份好配置——热重载最怕一个逗号把游戏弄死。

### 3.6 虚体与动画

- **一个实例抽不出共性，等第二个出现再抽。** 现在抽出来的"虚体"大概率会把 Button 特有的东西（点击、悬停、长按）当成共性带进去，而血条和 buff 不需要这些。等血条出现，两个实例的真实共性才显形。
- **动画是正交的一层，不是虚体的属性。** 实体也要动画（走路、举盾、受击闪白）。把动画放进虚体，写实体的第二天必然复制一份。
- **动画的落点就在适配器里。** 所以先做适配器不是拖延，是给动画挖好坑。
- **动画时间归逻辑侧，渲染层只读已算好的帧号。** 渲染层自己计时的话，打开暂停菜单时动画照样在走——而 `Pause` 状态已经存在。这也守住了"立即模式渲染"那条方法论。
- **位移表和状态表合成一张帧表。** 两张表会索引漂移（第 3 个位移配第 4 个图），调半小时才发现。
- **第一条动画不要做状态机，先做等时帧循环。** 动画系统的复杂度全在状态机（Idle → Walk → Attack 的转换条件），不在帧表。

### 3.7 工程习惯

- **适配器是"一组 8 行的 push 函数"，不是万能函数。** 每个逻辑集合一个 push，`drawLayer` 永不变。加一个品种的成本是"一个 push + 一条表项"，要能一眼说出这个数字。
- **DEVLOG 要记"否决过的方案"，不只记采用的方案。** 这是它比 README 值钱的地方——否则几个月后会把"对象池"再想一遍，还觉得是个新主意。

## 五、修订与补充

### 5.1 步骤顺序修订（业务优先）

§二 原先的顺序是按「结构债最重」排的，不是按「现在最该做什么」排的。修正为：

1. **跑通一个业务循环**：dt + 一个会动的矩形（允许 `RenderData` 临时加字段）
   判据：PuGame 里有东西按帧率无关地移动
2. **收窄渲染契约**（Config + 适配器 + drawLayer + 纹理缓存）
   触发条件：要画第二样东西，或要给实体贴图 / 播动画
3. **让数据离开代码**（JSON）
   触发条件：有 3~4 样东西的位置要反复调

理由：适配器的载荷（`DrawItem` 的字段、分层、`push*` 函数的边界）只能由业务逼出来。提前做是在猜，而猜出来的形状大概率错。

### 5.2 实体不是「虚体」

虚体（UI）的第二个实例是血条 / buff 图标。**实体是另一条线**：有运动、有碰撞、没有点击。
所以「实体出现」**不构成抽 Button / 抽虚体的理由**，判据不变：同类对象的第二个实例出现才抽。

实体的渲染走独立通道，不与 `buttons_` 合并；`Rect` 的 `int` 坐标也不适合实体（亚像素位移会被截断）。

### 5.3 渲染端拿「描述」，不拿「对象」

两种流派都成立：立即模式（数据 → 每帧重建描述）与保留模式（对象自带 draw）。
本项目选了立即模式，已写进 DEVLOG 方法论第 3 条。

若改成 `Entity` 自带 `draw()` + `visible`，代价是：

- `logic/` 会依赖 SFML **Graphics**（目前只依赖 SFML System，这是最干净的边界）
- `visible` 是「流程派生」状态，与 Button v1 的 `isHovered` 同类，必然长出注册/同步/销毁三件套
- 推翻已确立的方法论

**结论**：`View` 里只放中性 POD，不含 SFML 类型；`logic` 与 `render` 都只依赖这份描述。
领域语义（`alive` / `despawned`）留在实体里是**对的**；渲染决策（`visible` / `shouldDraw`）留在实体里是**错的**。

### 5.4 栈是控制流，不是渲染清单

现在「遍历栈 = 渲染层」成立，是因为每个状态的可见物恰好等于它自己。
一旦出现跨状态常驻的 HUD、预加载未显示的关卡、一个状态画两样东西，这条就不成立。

`collectView` 产出的 `View` 就是到时候的独立渲染清单。现在做它不算多余，它同时是未来仲裁管线的挂载点。

### 5.5 现在不做的三件事（附触发条件）

| 不做 | 触发条件 |
|---|---|
| 能力门控表 + 仲裁管线 | 出现「同一对象在不同系统里被区别对待」的规则（死亡后不可操作但可渲染、尸体可交互） |
| 按游戏模式拆 GameData + `gameData/` 目录 | 第二个游戏模式真的出现 |
| 完整渲染适配器（美术表 / drawLayer） | 要给实体贴图或播动画 |

能力门控管的是**多维度能力**（可操作 / 可碰撞 / 可渲染 / 可选中），不是一次渲染判断。
简化成对象上的一个 bool 会丢掉三样：多维、单一真相（表）、统一仲裁。
参考形态：UE 的 GameplayTags 阻塞、Godot 的 `process_mode`。
